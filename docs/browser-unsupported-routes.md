# Known unsupported and unverified PDF entry routes (opener-0813)

**Scope:** PDF Magic Opener's **automatic native ClamAV scan-before-render/interception**, not whether a browser itself can view, download or save a PDF. **As reviewed October 31, 2026, no such interception route is active in any of the nine registered browsers.** The shared WebExtension background is inert. This register records every unsupported/unverified entry route identified in the repository's existing deployment policy, bypass-path assessment, browser limitations and per-browser tests. It is not a claim that all possible future/browser-specific paths have been enumerated.

**Terminology matters.** `uncontrolled` means the current PDF Magic Opener integration has *no proven veto* over this entry route. `unverified` means a conditional browser API or path may exist, but effective permission, installed-version behavior, and native scanner enforcement have **not been established**. Neither status says the underlying browser is incapable of viewing a PDF. Neither is a successful scan, nor proof that all PDF opening is blocked; a PDF-viewer smoke-test pass is **not a successful scan**. The [machine-readable register](browser-unsupported-routes.json) is the source for the rows below; CI checks its completeness against the existing code-defined path lists.

| Browser ID | Browser | Current limitation | Effective automatic scan-before-render |

| `chrome` | Google Chrome | MV3 DNR matches rules only; blocking webRequest is enterprise-policy-installed-only; not a native scan response hold. | **Inactive** |
| `chromium` | Chromium | Version/build-specific DNR and response-viewer behavior unverified; no authenticated scanner interlock. | **Inactive** |
| `edge` | Microsoft Edge | MV3 DNR does not await native scan; webRequest blocking exception is enterprise policy installed only. | **Inactive** |
| `vivaldi` | Vivaldi | Chromium-derived API compatibility is conditional; PDF viewer, site grant and interception behavior unverified. | **Inactive** |
| `opera` | Opera | Downloads/Web Request API presence does not establish reliable native response blocking or fork parity. | **Inactive** |
| `arc` | Arc | Chrome extension support and browser viewer rendering do not establish a guaranteed pre-render interception point. | **Inactive** |
| `firefox` | Mozilla Firefox | Firefox response-stream filter and blocking webRequest need grants and a trusted, complete native scan/release integration not yet built. | **Inactive** |
| `safari` | Apple Safari | Safari's versioned DNR/network permissions and nativeMessaging host do not establish a universal byte-hold or scanner gate. | **Inactive** |

These are the nine IDs from [browser registry](../browser_registry.py), the [vendor research matrix](browser-automatic-interception-capabilities.json), and the [deployment capability matrix](../extensions/webextension/src/automatic-interception-capability-matrix.js). `documented` browser API support means *vendor API documentation*, not an installed/verifiable PDF Magic interception gate. Even Firefox's potential response-body filter is currently **inactive**. Apple Safari's `nativeMessaging` is not an interception authorization. Chrome and Edge normal MV3 installs cannot assume the enterprise-policy-only blocking `webRequest` exception.

## What existing browser tests actually verify

- **Viewing:** Chrome, Edge, Firefox, Brave and other browser smoke suites verify particular installed-version PDF reader behavior (where tested), including synthetic inline/extensionless, authenticated, concurrent and malformed examples. A rendered page is **not** a verdict from the native scanner. See [PDF viewer differences](browser-pdf-viewers.md), [authenticated endpoints](browser-authenticated-pdf-endpoints.md), [concurrent tabs](../extensions/webextension/concurrent-pdf-tabs.md) and [malformed responses](browser-malformed-remote-pdf.md). Other browser-specific verification may be pending; do not turn an open PR or unexecuted test into a production capability claim.
- **Downloads and opening:** Browser-native downloads, download shelf/history, automatic external opening, the system association, other extensions and Finder can be independent of a PDF Magic controlled native launch. See [controlled download opening](download-opening-browser-support.md), [native browser PDF downloads](browser-native-pdf-downloads.md), and [automatic opening test scope](download-automatic-browser-opening-test.md). The native `scan-and-open.py` pipeline independently protects *its own* handoff, but does not control all browser/OS paths.
- **API investigation:** DNR may block **matching network requests**, not await a complete native ClamAV verdict. Firefox blocking request/stream APIs have version and grant prerequisites; forks and Safari have separate limitations. No current extension proves effective before-render byte holding, scanner result correlation, or all-path coverage. See [vendor API research](browser-automatic-interception-research.md), [enforceable point assessment](../extensions/webextension/src/pdf-interception-point-assessment.md) and [disabled reliability policy](../extensions/webextension/src/automatic-interception-reliability.md).

## Required behavior when a route is unsupported or unverified

1. **Do not silently activate interception.** Do not infer a clean result from a URL, MIME type, DNR rule match, browser viewer, download completion, saved opt-in or available API. Keep the extension inactive and report effective interception honestly.
2. **Do not bypass existing safety.** If an explicit native-controlled scan-and-open request occurs, retain full byte identity, complete/fresh ClamAV scan, file identity/stability, quarantine, browser dangerous-download warnings and the user's verified chosen application. Block native opening on missing permission, failed/partial/late scan, mismatch, timeout or disconnection.
3. **Preserve the user's browser state.** Do not rewrite browser viewer/download defaults, system PDF associations, extension grants, file downloads, or custom target applications. Unsupported viewer shells may be offered a **separately eligible, explicitly user-triggered** scan action only after its own authentication and safety checks; never silently fetch private pages.
4. **Treat unrecognized paths and browsers as unverified and fail closed within PDF Magic Opener.** PDF Magic Opener **does not control all browser/OS paths**: this is **not** a browser/OS-wide lock, and the browser or other applications may still open PDFs independently. Never describe the passively documented behavior as enforced all-path protection.
5. **Before promoting any route**, independently prove installed browser/version and site permission, trusted request/tab/document identity, synchronous block *before actual render*, full response and native scanner identity, fresh signatures, bounded failure/restart handling, quarantine, and safe release. Record browser-specific evidence and update this register *and* its CI checks in the same change. Proving one viewer path does not authorize another.

## CI coverage and limits

The focused `extensions/webextension/tests/browser-unsupported-routes.test.mjs` test verifies catalog schema, unique IDs, coverage of **all** canonical and bypass route identifiers exported by existing code, exact browser registry/research parity, existence of linked evidence, the presence of every catalog row and browser in this document, the inactive extension manifest/background, and the absence of any claim that automatic interception or all-path opening protection has been enabled. It runs under the ordinary WebExtensions `npm test` wildcard **and** an explicit `scanner-tests` CI step. It does not run a network interception experiment or modify production scanner, manifests, permissions or preferences.
