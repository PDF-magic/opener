# Maximum filesystem restriction boundary (opener-0307)

This provides **real macOS kernel-enforced filesystem permissions** for the separate Maximum analysis process planned by opener-0306. That separate analyzer has **not been implemented or enabled** here. Maximum remains non-selectable; the active Built-in ClamAV scan, verified handoff, user preferences, cache, quarantine and browser configuration are unchanged.

Call \`run_maximum_filesystem_confined_worker(executable, arguments, pdf_bytes)\` from the future trusted worker orchestrator. The module refuses to run outside macOS, when \`/usr/bin/sandbox-exec\` is missing, or with invalid inputs, symlinked/untrusted binaries, oversized PDF bytes or invalid time budgets. There is **no unsandboxed fallback**. It uses Apple's Seatbelt profile with \`deny default\`: the worker may read required OS runtime files and its trusted executable but **may not read other user files or write any filesystem path**. The untrusted PDF is sent through an inherited stdin pipe so the sandbox never receives the PDF pathname. There is no network access rule, process-fork permission, or broad temporary-directory exception. The executable path is passed as a \`sandbox-exec -D\` policy parameter, never concatenated as executable sandbox syntax. The child gets a fixed minimal environment, root working directory, closed extra file descriptors and a bounded timeout. Its exit status is **not** a malware verdict; \`permits_open\` is always false.

The macOS sandbox-exec CLI is deprecated; do not assume it will remain supported. A missing/changed CLI or denied runtime dependency must fail closed rather than disable sandboxing. A production Maximum worker also requires its own dedicated helper lifecycle, capacity limits, secure result protocol, PDF behavior inspection and complete admission policy from other checklist tasks. This code intentionally does not create those features.

\`test-maximum-filesystem-sandbox.py\` exercises actual OS-denied attempts to read a private PDF, write a new file, and follow a symlink, while verifying permitted stdin-based execution. Other tests check input validation, missing sandbox, immutable non-authorizing outcomes and scanner isolation. A dedicated macOS GitHub Actions job runs the real kernel sandbox probes on pull requests and on main, alongside the original unchanged CI jobs.
