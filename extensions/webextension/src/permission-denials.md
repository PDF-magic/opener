# Denied browser permissions (opener-0589, §9.2)

`src/permission-denials.js` provides **shared fail-closed denial handling** for separately implemented optional browser permission flows. It is a passive, dependency-free controller; importing it neither requests permissions nor starts an extension feature. The current browser background remains inert and **no user preferences are read, changed, reset or persisted**.

Create `const handler = createPermissionDenialHandler(stopProtectedFeature)` with the existing feature's shutdown/unsubscribe function. Once a separately authorized permission request resolves, call `await handler.handle(outcome)` **only after awaiting the actual request**. For the future opt-in download monitoring helper (PR #378), `false` is an explicit denial and the shutdown callback should unsubscribe any active listeners. For the future optional per-site helper (PR #381), `{ status: "denied" }` is an explicit denial; an `unavailable` or malformed result likewise invokes shutdown and remains blocked.

Returned frozen states expose only `status`, a fixed non-sensitive `message` for accessible UI, `canProceed: false`, `scannerVerified: false`, and `authorizesOpen: false`. Status values are `unverified`, `denied`, `unavailable`, or `cleanup-failed`. A successful request is **not processed as scanner permission** by this helper: a `true` input leaves the state unverified and the real integration must independently validate effective current permissions and all native scanner gates before enabling any feature.

A denial permanently latches the controller, invokes shutdown **at most once** (including repeated, reentrant, and concurrent events), and returns generic guidance. If shutdown throws or rejects, `cleanup-failed` warns that resource teardown cannot be confirmed. It never exposes browser exception text, downloaded filenames or local paths to the UI. It never retries a permission prompt, silently enables an unrelated capability, or overwrites the user's stored opt-in preference. A future explicit user attempt can construct a new controller; simply receiving a later `true` cannot override an earlier denial.

**Integration prerequisite:** The permission request and browser feature wiring are separate checklist tasks. The existing extension has not activated download monitoring or native messaging. This module does not change any source or packaged manifest, add browser/site permissions, or wire an interactive popup control. It does not confer a ClamAV verdict or permit a PDF to be opened. ClamAV freshness, document integrity, quarantine and the selected destination application remain mandatory protections.

The existing Node.js WebExtensions `npm test` CI step automatically discovers `tests/permission-denials.test.mjs`, including cases for denial, unsupported APIs, malicious results, repeated or reentrant cleanup, failures, and import-time inactivity.
