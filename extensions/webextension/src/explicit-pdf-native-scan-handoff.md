# Submit an explicitly acquired PDF to the local scanner (opener-0772)

`createExplicitPdfNativeScanHandoff({ downloadsApi, permissionsApi, coordinator, scanGate })` connects an explicit **Scan This PDF** acquisition to the already reviewed `submitCompletedPdfDownloadToNative` adapter. The handoff performs a real submission to the **injected and independently authenticated** scanner coordinator after the safety gate permits it; it does not activate the transport-only native host or enable the installed extension.

The caller supplies three separately obtained records: the validated seven-field `describeExplicitPdfScanRequest` intent, the exact `download-started` result from the explicit download acquisition adapter, and the browser-owned `{ kind: "completed", id }` event for the **same** numeric download ID. An acquisition acknowledgment and a browser completion event are not proof of the selected file's identity or scanner readiness.

The trusted coordinator must supply its own `explicitPdfScanReady: true` and `nativeScannerReady: true` readiness fields and two own functions, `readVerifiedAcquiredPdf(reference)` and `submitCompletedPdfDownload({ id, localPath })`. The former must independently bind the currently selected PDF, originating real user action, tab/frame and request ID to the completed browser transfer, returning exactly `{ requestId, source, tabId, frameId, selectionId, downloadId, verified: true }`. A page, browser-supplied file path, or arbitrary JavaScript object cannot authenticate those facts. The handoff checks that exact association at entry, immediately before sending to native coordination, and after the accepted handoff. Changed callbacks, navigation and revoked readiness fail closed.

The shared completed-download submission adapter rechecks current downloads permission, browser revocations, transfer completion and byte counts, local-path consistency, PDF type, browser-native security warnings, and the persistent session-owned one-shot `createCompletedDownloadScanRequestGate`. That gate atomically reserves the browser download ID, preventing duplicate native submissions even if distinct explicit requests refer to the same transfer.

The coordinator's `{ accepted: true }` reply means **only** that the submission was acknowledged. It must independently revalidate the canonical local file, symlink and regular-file safety, file stability, current ClamAV signatures, malware scanning, quarantine, and scan-before-open policies. The return value deliberately fixes `scanVerified: false` and `authorizesOpen: false` and contains neither source URLs nor local paths. Native opening and user-selected PDF application behavior are untouched.

**Production prerequisite:** the currently shipped WebExtension remains inactive and has no live authenticated current-PDF-to-native scanner bridge. Its transport-only native host rejects untrusted browser paths. This task adds no browser permissions, native commands, automatic monitoring, download behavior, unsafe fallback or changes to stored user preferences. An independently reviewed real browser-to-native integration remains necessary to enable this handoff for users.

The 14 regression tests in `tests/explicit-pdf-native-scan-handoff.test.mjs` are picked up automatically by the mandatory WebExtensions `npm test` job in GitHub Actions. They verify successful coordination, malformed and mismatched request/transfer evidence, unsafe downloads, permission revocations, selection changes, duplicate request suppression, native failures, disposal and privacy.
