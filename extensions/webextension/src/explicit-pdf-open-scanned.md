# Open Scanned PDF action (opener-0774, §12.2)

`createOpenScannedPdfAction(root, coordinator, gate)` provides a **real, accessible, opt-in Open Scanned PDF button** in an extension-owned UI. It is intentionally inert until a separately authenticated, trusted current-PDF/native scanner integration is supplied. The currently shipped WebExtension background is inactive and has no live native opening credentials.

The injected coordinator must supply own `nativeScanResultsReady: true` and `nativeVerifiedOpeningReady: true`, and own `readCurrentSelectionId()`, `readVerifiedExplicitPdfScanResult({requestId, scanRequestId, selectionId})` and `requestVerifiedExplicitPdfOpen({scanRequestId})` methods. A readiness flag or JavaScript-supplied clean status is **not** authentication. The coordinator must attest the current selected PDF, native host session, complete ClamAV scan with fresh signatures, file identity/integrity and current permission independently.

The caller explicitly invokes `await offer({ requestId, scanRequestId, selectionId })` for a previously submitted Scan This PDF request. The helper accepts only a precise version-1 `scan.result` response envelope, with matching IDs, `status:"complete"`, `scanCompleted:true`, `scanVerified:true`, `authorizesOpen:false`, and `result:{status:"clean"}`. Malware, incomplete/failed/ambiguous results, inherited/getter data, navigation changes or missing native capability never offer an actionable button. This mirrors the separately scoped scan-result presentation contract without modifying that work.

The user must click the extension-owned **Open Scanned PDF** button. Script-triggered events are ignored. Before dispatch, the action re-reads the trusted scan proof and the current selection. A persistent, per-authenticated-session `createDownloadOpenCommandGate()` is supplied by the integration and synchronously reserves the opaque scan ID, preventing duplicate opening commands across views. It invokes the coordinator with only frozen `{ scanRequestId }`; no URL, file path, PDF bytes, browser metadata, or user-selected app override is sent. The coordinator must independently revalidate the actual native file, clean scan, signature freshness, quarantine and saved PDF app selection at **final opening**, and reject changed files or invalid sessions. Neither a clean result nor an accepted opening command is authorization for the JavaScript UI to launch the PDF.

A response of exactly `{ accepted: true, scanRequestId }` means only **request submitted**, never that the PDF actually opened. Returned frozen states always have `scanVerified:false`, `authorizesOpen:false` and `opened:false`. A pending, refused or stale action cannot claim success. Clearing/disposal removes listeners, invalidates old requests and hides the button. The shared gate retains used IDs for the native session.

**Production prerequisite:** the transport-only native host still rejects browser-initiated filesystem scan/open requests, and the installed extension has no authenticated coordinator. This task does **not** register a listener, change permissions/manifest/scanner behavior, bypass quarantine, request a PDF opening on startup, or modify stored user preferences. Native integration must be reviewed and enabled separately.

The 13 regression test groups in `tests/explicit-pdf-open-scanned.test.mjs` run in existing WebExtensions `npm test` and required `scanner-tests` GitHub Actions, covering verified cleanliness, visible controls, real clicks, stale selections, duplicate opens, malicious reports, native failures and unchanged safety boundaries.
