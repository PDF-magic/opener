# Scanner transfer for an intercepted PDF (opener-0784)

**Decision: a design-only, fail-closed native handoff contract; automatic interception remains disabled.** The pure `describeInterceptedPdfScannerTransfer(input)` function supplies an immutable, bounded routing plan, not a transfer, native scan command, clean verdict or PDF-open authorization. No supported browser currently has a tested end-to-end pre-render scanner interlock. This task does not install listeners, request permissions, move browser settings or change user preferences.

## Two distinct routes

**1. Potential before-render response stream — Firefox only, conditional.** A separately implemented and verified Firefox `webRequest.filterResponseData` response filter (with effective webRequest, webRequestBlocking, webRequestFilterResponse and host grants) could hold an *eligible* main-frame PDF response. A trusted adapter would correlate an opaque capture ID and browser request ID through the final redirected response, recheck current origin/site consent, verify the complete PDF bytes and stream them into a **native-owned, private, atomic quarantine spool**, never an extension-selected filesystem path. Transfer must be bounded by the **existing 100 MiB total / 8 MiB chunk** limits through `copyExplicitPdfWithinSizeLimit`, plus a separately enforced timeout, backpressure, abort on partial write or disconnection, and final byte-completeness and PDF-content checks. Do not buffer an unbounded document in the extension or send arbitrary page URLs, signed links, cookies, tokens, raw file paths or scanner verdicts over the transport-only native host.

After an independently authenticated bridge has committed the entire private spool, a trusted native coordinator must bind the final response, tab/main frame, capture and request IDs to the staged regular file and stable identity, check ClamAV signature freshness, scan, quarantine if required and release the held response **only on an independently correlated clean verdict and current permission**. Errors, redirects not revalidated, timeout, revocation, browser worker restart, changed file identity, partial bytes and native disconnect fail closed; terminate or abort the held filter and clean the partial spool. A `filterResponseData` stream must always be closed or disconnected according to the browser API contract. Whether the native verdict can safely gate original rendering needs separate live-browser implementation and tests. The stream bridge and native spool/scan integration are **not implemented**. This is *not* proof of all-path interception.

**2. Completed browser download — post-download scanning only.** For browsers whose download events are established as observable (all current registered browsers except Safari), an independently trusted adapter may match the original request/capture to the *exact* completed browser download ID, then reuse `submitCompletedPdfDownloadToNative` and the existing session-owned `createCompletedDownloadScanRequestGate`. The existing adapter checks downloads permission, stable local path, MIME/PDF type, completion, bytes and browser-native danger warnings; the separately trusted native scanner revalidates file identity and performs scanning and quarantine. Do not auto-accept dangerous downloads. Download events occur **after download starts** and provide **no pre-render or pre-open guarantee**. They are not substitutes for an enforceable before-render interception point, including on Firefox. Safari's download-event path is not established and is rejected by the plan.

## Versioned contract and trust boundary

The eight exact, scalar input fields are `version: 1`, `browserId`, `source` (`response-stream` or `completed-download`), `requestId`, `captureId`, `tabId`, `frameId: 0`, and `maxBytes`. Identifiers are separate, bounded, opaque correlation values, **not access tokens**. No URLs, signed URL query strings, credentials, headers, PDF bodies, local file paths or claimed security flags are admitted. The maximum byte budget cannot exceed the existing 100 MiB hard limit; the planned chunk size is at most 8 MiB. The function rejects unknown browsers, unsupported sources, non-main-frame requests, extra fields, malformed budgets and hostile accessors. The output is immutable and explicitly sets `scannerTransferReady`, `automaticInterceptionEnabled`, `preRenderGuaranteed`, `scanVerified`, `authorizesScan`, and `authorizesOpen` to false.

The contract is **not** evidence that a response has actually been blocked, captured, streamed, scanned or authorized. A real integration must attest browser/version and effective revocable grants, genuine opt-in, original and final redirected response identity, exact complete PDF bytes and timestamps, native session ownership, private staging, current file identity, native anti-malware scanning, cleanup and independent clean-result correlation. If any gate is missing, the browser must not present a successful scan or authorize opening. The current native-messaging entry point deliberately rejects arbitrary browser-supplied paths and must not be bypassed.

A browser extension cannot guarantee scan-before-open for cached/inline PDF paths, blob:/data:/file: URLs, unmatched or redirected requests, browser auto-open and other extensions, Finder, or other OS applications. Preserve existing scanner safety, native quarantine behavior, the default PDF application, browser dangerous-download warnings and user preferences. Never silently re-fetch signed links or swap in an unverified copy when a stream fails.

## Verification and follow-up

`tests/intercepted-pdf-scanner-transfer.test.mjs` runs under the existing WebExtensions `npm test` CI job. It checks routing restrictions across nine supported browsers, bounded transfer metadata, immutable and private-only descriptors, hostile inputs, explicit no-scan/no-open status and the unchanged inert background and manifest. End-to-end integration remains a **separate prerequisite**: live interception/stream filter and native-owned staging, independent authentication, per-browser permission and timing tests, reliable fail-closed held-response lifecycle and actual ClamAV result correlation. The pure plan alone cannot deliver bytes to the scanner.
